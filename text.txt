==============================
EXPERIMENT 15: ANALYSING ANDROID APP PERMISSIONS AND MOBILE TRAFFIC
===================================================================

PROCEDURE

---

## STEP 1: Create Android Virtual Device (AVD)

1. Install and open Android Studio
2. Open AVD Manager
3. Click Create Virtual Device
4. Select a device (Pixel 2 / Pixel 9)
5. Complete setup and download system image

---

## STEP 2: Start Emulator with Proxy

1. Open Command Prompt

2. Go to:
   cd C:\Users\Admin\AppData\Local\Android\Sdk\emulator

3. Run:
   emulator -list-avds

4. Start emulator:
   emulator -avd Pixel_9 -http-proxy http://10.0.2.2:8080

---

## STEP 3: Configure Proxy in Emulator

1. Go to Settings
2. Network & Internet → Internet → Edit → Advanced options
3. Set Proxy to Manual
4. Hostname: 10.0.2.2
5. Port: 8080
6. Save

---

## STEP 4: (If proxy not saving – use ADB)

1. Go to:
   cd C:\Users\Admin\AppData\Local\Android\Sdk\platform-tools

2. Run:
   adb devices

3. Set proxy:
   adb shell settings put global http_proxy 10.0.2.2:8080

4. Verify:
   adb shell settings get global http_proxy

---

## STEP 5: Configure Burp Suite

1. Open Burp Suite
2. Go to Proxy → Options
3. Proxy Listeners → Edit → Select All Interfaces
4. Turn Intercept ON

---

## STEP 6: Capture HTTP Traffic

1. Open Chrome in emulator
2. Visit http://example.com
3. Check Burp Suite → Proxy → HTTP History

---

## STEP 7: Download Burp CA Certificate

1. Go to Proxy → Options → Import/Export CA Certificate
2. Select Certificate in DER format
3. Save as burpcer.der

---

## STEP 8: Install Certificate in Emulator

1. Run:
   adb push C:\Users\Admin\Downloads\burpcer.der /sdcard/Download/

2. In emulator:
   Settings → Security & Privacy → More Security & Privacy
   → Encryption & Credentials → Install Certificate → CA Certificate
   → Select burpcer.der

---

## STEP 9: Verify HTTPS Interception

1. Open Chrome in emulator
2. Visit https://example.com or https://wikipedia.com
3. Check Burp Suite → Proxy → HTTP History

OBSERVATION

---

1. HTTP traffic was successfully captured in Burp Suite under Proxy → HTTP History
2. Requests and responses for websites like example.com were visible in plain text
3. After installing the CA certificate, HTTPS traffic was also intercepted successfully
4. Secure (HTTPS) requests were decrypted and displayed in Burp Suite
5. Headers, cookies, and request parameters were visible for analysis
6. Without CA certificate, HTTPS traffic was not visible or appeared encrypted
7. Proxy configuration (10.0.2.2:8080) successfully routed emulator traffic through Burp Suite
8. Intercept ON allowed modification of requests before forwarding
9. Intercept OFF allowed normal browsing while still logging traffic

EXPERIMENT 17: CREATING AND ANALYZING DISK IMAGES USING dc3dd AND AUTOPSY
=========================================================================

PROCEDURE

---

## STEP 1: Open Terminal in Kali Linux

1. Press:
   Ctrl + Alt + T
2. Terminal will open

---

## STEP 2: Create Sample Evidence

1. Create a sample file:
   echo "Cybersecurity Lab Evidence" > evidence.txt

2. Verify file:
   ls

---

## STEP 3: Identify Disk Partition

1. List storage devices:
   lsblk

2. Identify partition (e.g., /dev/sda1)

---

## STEP 4: Create Disk Image (Using dc3dd/dd)

1. Create a disk image file:
   dd if=/dev/zero of=practice_disk.dd bs=1M count=100

2. This creates a 100MB disk image

3. (Optional forensic step using dc3dd with hashing)
   dc3dd if=/dev/sda of=/home/kali/disk_image.dd hash=md5 log=/home/kali/acquisition.log

4. This performs:

* Bit-by-bit copy
* Generates hash value
* Creates log file

---

## STEP 5: Format and Mount Disk Image

1. Format disk:
   mkfs.ext4 practice_disk.dd

2. Create mount directory:
   mkdir /mnt/disk

3. Mount disk:
   sudo mount -o loop practice_disk.dd /mnt/disk

4. Copy evidence file:
   cp evidence.txt /mnt/disk/

5. Unmount disk:
   sudo umount /mnt/disk

---

## STEP 6: Verify Image Creation

1. Check image file:
   ls -lh /home/kali/disk_image.dd

2. View log file:
   cat /home/kali/acquisition.log

3. Verify:

* Image size
* Hash value
* Acquisition details

---

## STEP 7: Start Autopsy

1. Run:
   autopsy

2. Open browser and go to:
   http://localhost:9999/autopsy

---

## STEP 8: Create New Case in Autopsy

1. Click "Create New Case"
2. Enter case name and details
3. Click Next

---

## STEP 9: Add Disk Image

1. Select:
   Add Host → Add Image

2. Browse and select:
   /home/kali/disk_image.dd

3. Proceed with default settings

4. Start analysis

---

## STEP 10: Analyze Evidence

1. Explore file system in Autopsy
2. Locate created file (evidence.txt)
3. Check:

* File metadata
* Deleted files
* Logs and artifacts

4. Extract relevant evidence if needed

OBSERVATION

---

1. Disk image was successfully created as a bit-by-bit copy
2. Hash value (MD5) was generated ensuring data integrity
3. Log file recorded acquisition details (time, size, hash)
4. Disk image contained the created evidence file
5. Mounted disk allowed insertion of sample forensic data
6. Autopsy successfully loaded and analyzed the disk image
7. File system structure was visible in Autopsy interface
8. Evidence file (evidence.txt) was detected during analysis
9. Metadata such as file size, timestamps, and location were accessible
10. Deleted files and system artifacts could be explored
11. No modification was made to original data ensuring forensic integrity

EXPERIMENT 18: LOG FILE ANALYSIS FOR INCIDENT DETECTION
=======================================================

PROCEDURE

---

## STEP 1: Navigate to Log Directory

1. Open terminal

2. Run:
   cd /var/log

3. List files:
   ls

4. Observe log files:

* dpkg.log
* apache2
* nginx
* journal
* wtmp, btmp

---

## STEP 2: Check Successful Logins

1. Run:
   last

2. Observe login history

---

## STEP 3: View System Logs

1. Run:
   journalctl | less

2. Scroll through logs

---

## STEP 4: Detect Failed SSH Attempts

1. Run:
   journalctl | grep "Failed"

2. Observe failed authentication attempts

---

## STEP 5: Analyze SSH Activity

1. Run:
   journalctl | grep ssh

2. Observe login attempts and connections

---

## STEP 6: Detect Errors

1. Run:
   journalctl | grep -i error

2. Observe system errors

---

## STEP 7: Analyze Apache Logs

1. Navigate:
   cd /var/log/apache2

2. List files:
   ls

3. Open access log:
   sudo less access.log

---

## STEP 8: Identify Suspicious Requests

1. Run:
   grep "404" /var/log/apache2/access.log

2. Observe failed requests

---

## STEP 9: Check Package Activity

1. Run:
   less /var/log/dpkg.log

2. Observe installation and update logs

---

## STEP 10: Real-Time Monitoring

1. Run:
   sudo journalctl -f

2. Observe live logs

---

## STEP 11: Simulate Failed SSH Login

1. Install SSH:
   sudo apt install openssh-server -y

2. Start service:
   sudo service ssh start

3. Find IP:
   ip a

4. Attempt wrong login:
   ssh fakeuser@localhost
   OR
   ssh kali@localhost

5. Enter wrong password multiple times

---

## STEP 12: Analyze Failed Login Attempts

1. Run:
   journalctl | grep "Failed password"

2. Extract IP:
   journalctl | grep "Failed password" | awk '{print $11}'

3. Count attempts:
   journalctl | grep "Failed password" | awk '{print $11}' | sort | uniq -c | sort -nr

---

## STEP 13: Alternative Method (lastb)

1. Run:
   sudo lastb

2. Observe failed login records

---

## STEP 14: Check Recent Activity

1. Run:
   journalctl --since "10 minutes ago"

2. Observe recent logs

OBSERVATION

---

1. Log directory (/var/log) contains important system and application logs 
2. Successful login history was observed using the "last" command 
3. System logs displayed various services, authentication events, and activities 
4. Failed login attempts were detected using journalctl grep "Failed" 
5. SSH logs showed login attempts and connections 
6. Error logs indicated system issues or abnormal behavior 
7. Apache logs recorded web requests and user activity 
8. Multiple 404 errors indicated possible scanning or probing attempts 
9. Package logs showed installation and update activities 
10. Real-time monitoring displayed live system activity 
11. Simulated failed SSH login attempts were successfully recorded in logs 
12. Repeated failed login attempts from the same IP (e.g., 127.0.0.1) were identified 
13. High frequency login attempts indicated brute force attack behavior 
14. Suspicious IPs were identified based on repeated failed attempts 
15. System logs also showed normal activities such as CRON jobs, services, and user commands 
16. Repeated kernel messages (VirtualBox related) were observed, indicating abnormal but non-malicious behavior

EXPERIMENT 21: CONDUCTING A SECURITY AUDIT AND RISK ASSESSMENT
==============================================================

PROCEDURE

---

## STEP 1: System Information

1. Press Windows + R

2. Type:
   msinfo32

3. Note:

* OS Version
* System Type

---

## STEP 2: Check Windows Updates

1. Open Settings
2. Go to Windows Update
3. Click Check for updates

---

## STEP 3: Check Firewall Status

1. Search: Windows Defender Firewall
2. Click Turn Windows Defender Firewall on or off

---

## STEP 4: Check Antivirus (Windows Security)

1. Open Windows Security

2. Go to Virus & Threat Protection

3. Check:

* Real-time protection → ON
* Last scan → Recent

---

## STEP 5: Check Password & Account Security

1. Go to:
   Settings → Accounts → Sign-in options

2. Check:

* Password / PIN enabled
* Windows Hello (optional)

---

## STEP 6: Check Installed Applications

1. Go to:
   Settings → Apps → Installed apps

2. Look for:

* Unknown software
* Cracked tools

---

## STEP 7: Check Startup Programs

1. Press:
   Ctrl + Shift + Esc

2. Go to Startup tab

3. Disable:

* Unknown apps

---

## STEP 8: Check Network Security

1. Go to:
   Settings → Network & Internet

2. Check:

* WiFi connection
* Network type (Private/Public)

---

## STEP 9: Check Browser Security

1. Open Chrome/Edge

2. Go to:
   Settings → Privacy & Security

3. Check:

* Safe browsing ON
* Remove unknown extensions

---

## STEP 10: Check Data Backup

1. Search:
   Backup settings

2. Check:

* OneDrive / External backup

---

## STEP 11: Risk Assessment

1. Identify:

* Assets
* Threats
* Vulnerabilities

2. Determine risk level (Low / Medium / High)

---

## STEP 12: Security Recommendations

1. Technical Controls:

* Enable firewall
* Enable antivirus
* Perform regular updates

2. Administrative Controls:

* Use strong passwords
* Avoid unknown downloads

3. User Awareness:

* Avoid phishing links
* Practice safe browsing

---

## STEP 13: Result

System vulnerabilities identified and mitigation strategies suggested

OBSERVATION

---

1. System information showed Windows 11 (64-bit) with Secure Boot enabled 
2. Windows updates were pending, indicating potential exposure to vulnerabilities 
3. Firewall was active and managed by third-party antivirus (Kaspersky) 
4. Antivirus protection was active with no current threats detected 
5. Account security included password and PIN authentication 
6. Installed applications did not include suspicious or unauthorized software 
7. Some startup applications were enabled, which may impact performance and security 
8. System was connected to a Wi-Fi network with Public network profile enabled 
9. Browser security had Safe Browsing enabled for protection against malicious sites 
10. Data backup (OneDrive) was not configured, increasing risk of data loss 
11. Risk assessment identified issues such as no backup, public network usage, and potential weak passwords 
12. Security recommendations included enabling backups, using strong passwords, and maintaining updates
